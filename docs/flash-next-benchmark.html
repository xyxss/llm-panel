Total fast memory is 16 GB VRAM + 30 GiB RAM ≈ 39 GB. The smallest usable quant is 67.6 GiB. Every configuration below streams the remainder from NVMe on every token — that constraint explains nearly every result.

Why the quant label is misleading

Reading the GGUF tensor headers first changed the whole approach. per_layer_token_embd.weight — the 51.2B-parameter n-gram embedding table — is pinned at IQ4_NL, 26.82 GiB, in every UD quant. So is every ffn_down_exps layer. Roughly 40 GiB of each file is byte-identical no matter which quant you pick.

The engram table is a sparse row lookup — about 2.7 KB read per token. It belongs on disk permanently, and llama.cpp's --lazy-mode already does that by default for tensors over 4 GiB. Only the hot transformer column competes for memory, which is what makes the quant comparison lopsided.

Note the shape: moving from 5.9 GB to 13.7 GB of VRAM buys only +37%, and 36 is a hard wall. VRAM is a weak lever here because just 10 of 512 experts fire per token — the binding constraint is the 30 GiB of system RAM acting as page cache.

Context ceiling

Gated DeltaNet is linear attention: only 12 of 48 layers are true sparse attention, so KV is unusually cheap — ~1,120 MiB per 32k at f16, ~560 MiB at q8_0. Switching to q8_0 is what puts full native context in reach.

Validation under a real prompt

Peak VRAM grows with prompt length, so a configuration that survives a 3k-token prompt can still die on a long one. The shipping speed preset was re-driven with a 20,596-token prompt — six times longer.

Peak rose only 170 MiB across a 6.6× longer prompt, so the 1.2 GB margin holds. Prefill more than doubled to 124.5 tok/s — batching pays off at length, and it is the reason a short prompt cannot be used to judge this model. Decode drops to 12.47 once the context is genuinely occupied; that is the number to expect in real use, not the 16.94 headline.

Quant verdict

IQ3_XXS beats Q4_K_XL by 1.97× on decode and 3.3× on prefill (65.6 vs 19.6 tok/s). Q4_K_XL also OOMs at n-cpu-moe 40, so it can never reach the fast split. Its hot transformer is 76.9 GiB against ~39 GB of fast memory — it simply pages far more per token. Deleted.

MTP: built, measured, rejected

Mainline llama.cpp has the qwen4exp architecture but not its MTP draft graph. Both published head variants fail to load — the shared one is missing token_embd.weight, the non-shared one output_hc_norm.weight. Getting an answer required building Unsloth's qwen4exp/mtp fork, after which MTP works: draft acceptance 33–38%, mean accepted length ~2.7 tokens.

MTP verdict — this model only

Best case is +7.4%, but the draft head costs ~2.8 GB and therefore OOMs at n-cpu-moe 40, forcing the slower split. Net result: 13.10 with MTP vs 16.66 without — 21% slower, and prefill drops a third. The opposite of Qwen3.8-27B, where MTP gives +45–65%, because that model fits in VRAM and is compute-bound while this one is bound by streaming weights from RAM and disk. Fork deleted.

How this compares

Published configurations for this model all use 64 GB or more of total memory. At 46 GB this is the memory-poorest setup in the sample, yet it lands mid-pack — because the engram table, which is a third of the file, was never the bottleneck.

Dead ends, so nobody repeats them

  • Low quants are a trap. Q2_K_XL saves only 2.8 GiB over IQ3_XXS and IQ1_S only 8.7 GiB, because ~40 GiB of every file is pinned at IQ4_NL regardless of label.
  • Don't pin the engram table with -ot ...=CPU. It competes with --lazy-mode, which already handles it.
  • Short prompts lie about prefill. The same server reports ~20 tok/s on a 20-token prompt, 56.6 on a 3,120-token one, and 124.5 on a 20,596-token one. Prefill is a function of prompt length here, not a property of the config.
  • Warm up before believing anything. The first request after a restart runs at ~10 tok/s until the page cache fills. Run-to-run spread is ±1.5 tok/s.
  • Loading is not working. Peak VRAM during prompt processing is what kills a config, and it never shows up in a load-only test.
